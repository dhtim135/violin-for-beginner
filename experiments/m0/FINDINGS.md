# M0 findings and implementation decisions

**Proceed with the shared score viewer and MusicXML import. Keep recognition results editable.** This local run covered four generated phrases, three published scores and five recorded pieces. Several variants reuse the same music. The results measure these examples on one Apple Silicon machine.

| Experiment | Measured outcome | Implication |
| --- | --- | --- |
| Annotated print | Visually inspected one A4 PDF with two staff systems. All 14 reference labels stayed under their notes, including low/high second fingers. | Use OSMD and test page breaks and resize behavior on longer scores in M1. [Print example](../../output/pdf/four-string-example.pdf) |
| Simple score recognition | Each of four two-bar phrases round-tripped exactly from PDF, PNG and skewed JPEG. Each import took 2.7–6.7 seconds. Exact here means the ordered pitches/rests and durations matched. | Audiveris is a reasonable worker candidate for clean, printed, single-part music. Phone lighting, perspective and handwritten music need separate evidence. [Measurements](results/omr-results.json) |
| Multi-part PDFs | First eight bars, voice and piano, with the first recognized part treated as the melody. Ordered matching events were 11/16, 26/38 and 4/30. Two imports changed the part count. | Show source, detected parts and audition together. Prefer an available structured edition. These measurements include engraving, pagination, recognition and automatic part choice. They do not isolate the cause of each error. [Measurements](results/edition-results.json) |
| Title retrieval | Searched 1,462 MXL paths. Three known titles returned retrievable scores with named voice and keyboard parts. The deliberately absent title returned zero. | Start with an edition catalogue and persist the chosen source URL. This corpus establishes retrieval feasibility within its own repertoire. [Retrieved editions](results/search-results.json) |
| Sampled violin phrases | Solo clips matched 25/28 expected pitch and onset pairs, with 35 suggestions. Adding a chord gave 24/28 with 45 suggestions. Only 22 and 17 matches respectively also had the correct duration on the supplied grid. | Quantizing detected pitches requires its own review step even at a known tempo. [Measurements](results/audio-results.json) |
| Recorded violin | Across five solos, 215 of 224 reference notes matched pitch and onset, from 315 suggestions. Of the 215 matches, 155 also ended within tolerance. | Preserve source audio alongside the suggestion. Extra attacks need a delete/merge gesture in the correction prototype. [Measurements](results/recording-results.json) |
| Recorded quartet | On the same pieces with accompaniment, 184 of 224 reference notes matched, from 744 suggestions. Only 101 matches also ended within tolerance. | Highest pitch among nearby attacks produces far too many unwanted notes for a beginner. Evaluate melody tracking or separation before offering a full-mix draft. [Measurements](results/recording-results.json) |

Recorded-audio matching used identical MIDI pitch, onset within 100 ms, and offset within 150 ms, with one-to-one matching against Bach10 violin annotations. The experiment evaluates timed note suggestions. Inferring meter, tempo, barlines and readable rhythms from real recordings remains an open task. Time to correct a draft with a beginner has yet to be measured.

## Delivery sequence

1. **M1, shared score experience.** Start with a public MusicXML edition and a hand-checked reference. Store score revisions locally. Implement first-position candidate fingerings across G/D/A/E, retaining manual choices. Deliver when an edit survives reopening and is reflected in synchronized playback, count-in, tempo changes, loops and the annotated PDF. Include ties, repeats, rests, print page breaks and out-of-range pitches in the checks.
2. **M2, image and PDF import.** Run Audiveris outside the interactive request. Expose the source page and selectable parts. Validate with real phone photos and multi-page scores. Measure corrections per bar and time to a playable draft.
3. **M3, title search.** Expose edition choices from the tested catalogue and import the selected part into M1. Include disambiguation and missing-source cases. Test coverage against the user's own repertoire before selecting broader providers.
4. **M4, audio.** Compare a melody tracker against the recorded solo and ensemble baselines. Deliver segment selection, source/draft audition, beat estimation, and editing for inserted or missing notes. Set supported input limits from measured correction effort.
5. **M5, integration.** Exercise each route through corrections, playback, save/reopen and printing. Document supported material and recovery from failed or uncertain conversions.

The proposed local architecture is a browser score view, a Python API and one conversion worker, with local files for media and persisted score revisions. Choose storage and queue infrastructure when implementing persistence and retries. The experiments ran without cloud resources. Production library licensing, accounts, hosting and deployment remain open.
